## D1 — 정산조건 6개로 충분한가

**결론: 충분하다. 단, `expected_date_source`가 있어야 충분해진다.**

6개로 커버 못 하는 실제 케이스가 세 가지 있다.

| 케이스 | 빈도 | 처리 |
| --- | --- | --- |
| 선금/잔금 분할 지급 | 흔함 | **계약 2건으로 나눠 등록.** MVP는 1계약 = 1입금 |
| 월 정액 리테이너 | 가끔 | MVP 범위 밖 |
| 익익월 말일 등 변칙 | 드묾 | `UNKNOWN` → 사용자가 예정입금일 직접 입력 |

분할 지급을 제대로 지원하려면 계약 1건에 입금 스케줄 여러 줄을 붙여야 해서
테이블이 하나 더 생긴다. 5일 안에 할 일이 아니다. 2건 등록으로 우회한다.

**`expected_date_source`를 추가한 이유**
`UNKNOWN`이면 `expected_date`가 null이 되는데, 그 계약은 D-day 계산에서 영원히 빠진다.
사용자가 직접 날짜를 넣을 수 있어야 하고, 그 값을 엔진이 재계산으로 덮어쓰면 안 된다.
이 탈출구가 있어서 enum을 6개로 유지할 수 있다.

> B에게 전달: **AI 프롬프트는 이 6개 값 외의 문자열을 절대 출력하지 않는다.**
> 판단이 안 서면 `UNKNOWN`을 내보내고 `missingFields`에 `settlementTerm`을 넣는다.

## D3 — 지연·위험 계약은 왜 "오늘" 기준으로 재계산하나

> ⚠️ 이 항목도 "확정 사항"이 아니라 **A 제안, B·C 승인 대기** 상태입니다.

예정입금일이 이미 지난 계약(지연·위험 상태)에 원래 시나리오 공식을
그대로 적용하면(예정입금일 + 지연일수), 그 결과가 **오늘보다도 과거**가
나올 수 있습니다. 이미 지난 날짜를 "예정 유입일"로 잡으면 D-day 계산이
왜곡됩니다.

그래서 지연·위험 상태인 계약은 예정입금일 대신 **오늘을 기준일로 재계산**합니다.

```
낙관 = 오늘
기준 = 오늘 + (거래처 중앙값 지연일 또는 신규거래처 기본값 7일)
비관 = 오늘 + (거래처 p90 지연일 또는 신규거래처 기본값 21일)
```

`policy.ts`, `engine-interface.md`에는 이미 이 방식으로 반영해뒀지만,
"지연 계약도 그냥 예정입금일 기준을 유지해야 한다"는 의견이 있을 수 있어서
팀 승인 전까지는 최종 결정으로 보지 않습니다.

## D7 — 원안 그대로 적용하면 깨진다

> ⚠️ 이 항목은 "확정 사항"이 아니라 **A 제안, B·C 승인 대기** 상태입니다.
> 아래는 A가 이렇게 계산해야 한다고 판단한 근거이고, 이미 코드(`policy.ts`)에는
> 반영했지만 팀 승인 전까지는 최종 결정이 아닙니다.

원안:
```
safe    : 잔액 >= 안전예비금
caution : 안전예비금 × 0.3 <= 잔액 < 안전예비금
danger  : 잔액 < 안전예비금 × 0.3
```

데모 계정은 `safetyBuffer = 0`이다(D10-A). 대입하면:
```
safe    : 잔액 >= 0
caution : 0 <= 잔액 < 0   ← 빈 구간
danger  : 잔액 < 0
```
**caution이 사라져 3단계가 2단계로 무너진다.** 캘린더 색이 두 가지만 나온다.

**보정: 기준선에 fallback을 둔다.**
```
referenceAmount = safetyBuffer > 0 ? safetyBuffer : monthlyFixedOutflow × 0.5
```

데모 계정 적용 결과 (기준선 600,000원):

| 구간 | 범위 | 기준 시나리오 60일 |
| --- | --- | --- |
| safe | ≥ 600,000 | 7일 |
| caution | 180,000 ~ 600,000 | 18일 |
| danger | < 180,000 | 35일 |

최초 caution 2026-09-06, 최초 danger 2026-09-26, D-day 2026-09-30.
캘린더에 색이 자연스럽게 번지는 구간이 나온다.

> [2026-09-03 재검증] hsoo23이 D10-A와 함께 재확인을 요청한 항목. D10-A의 buffer=0 행이
> (재검증 결과) 그대로 확정 유지되므로, 여기서 쓰는 fallback 기준선 600,000원과 위 표
> 전체가 그대로 유효합니다. `test/engine-verify.ts`로 실행해도 동일한 값이 나옵니다.

## D10-A — 안전예비금을 0원으로 두는 이유

페르소나는 잔액 800,000원, 월 필수지출 1,200,000원이다.
안전예비금 제안값(월 필수지출 1개월치)은 1,200,000원으로 **잔액보다 크다.**

제안값을 그대로 쓰면 `simulationStartBalance = -400,000원`이 되고,
**D-day가 첫 화면부터 "오늘"로 고정된다.** 선금 가정을 해도 D-day가 안 움직여서
데모 클라이맥스가 통째로 죽는다.

실측 비교 [2026-09-03 hsoo23 리뷰 요청으로 재검증 — 아래 표로 교체]:

> 이전 버전의 이 표(1일차 값)에서 "300,000 → 없음"이 안전예비금과 D-day의 단조 관계를
> 깼습니다(hsoo23 지적, D10-A). 재확인해보니 엔진 완성 전 값이 그대로 남아있던 것이었고,
> 실제로 재실행하면 buffer가 작아질수록 D-day가 단조적으로 늦어집니다. 낙관 열의 "없음"도
> 실제로는 측정 안 하고 비워둔 자리였습니다. 아래가 현재 브랜치로 재실행한 값입니다.

| 안전예비금 | simulationStartBalance | 낙관 | 기준 | 비관 |
| --- | --- | --- | --- | --- |
| 1,200,000 (제안값) | -400,000 | D-43 (2026-10-14) | **D-0** (2026-09-01) | **D-0** (2026-09-01) |
| 600,000 | 200,000 | D-43 (2026-10-14) | D-4 (2026-09-05) | D-4 (2026-09-05) |
| 300,000 | 500,000 | D-46 (2026-10-17) | D-22 (2026-09-23) | D-12 (2026-09-13) |
| **0 (확정)** | 800,000 | **D-53** (2026-10-24) | **D-29** (2026-09-30) | **D-13** (2026-09-14) |

기획서 3-3이 "0원으로 시작"을 명시적으로 허용한다. 억지로 맞춘 게 아니다.
온보딩에서 제안값 1,200,000원을 보여주고 사용자가 0원을 고르는 흐름을 데모에 넣으면
"잔액이 한 달 지출보다 적은 프리랜서"라는 현실이 그대로 드러나 오히려 설득력이 는다.
