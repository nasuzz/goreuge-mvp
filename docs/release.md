# 배포·제출 런북 (이슈 #9)

DRI: C. 검수: A·B.

배포부터 제출본 태그까지 순서대로 따라가는 문서다. 값은 전부 실측으로 확인한 것이며,
근거 명령을 함께 적었다. 숫자가 안 맞으면 이 문서가 아니라 실측을 믿고, 실측이 바뀌었으면
이 문서를 고친다.

## 1. Vercel 배포

### 1-1. 프로젝트 설정

`web/`이 저장소 루트가 아니므로 **Root Directory 지정이 필수**다. 루트 `package.json`은
`name: goreuge-shared` / `type: commonjs`이고 Next 앱이 아니다.

| 항목 | 값 |
|---|---|
| Root Directory | `web` |
| Framework Preset | Next.js (자동 감지) |
| Build Command | 기본값 (`next build`) |

`vercel.json`으로는 Root Directory를 지정할 수 없다. 대시보드에서 설정해야 한다.

### 1-2. 환경변수

| 키 | 값 | 비고 |
|---|---|---|
| `SUPABASE_URL` | A가 공유한 값 | |
| `SUPABASE_SECRET_KEY` | A가 공유한 값 | `NEXT_PUBLIC_` 접두사 금지 (D5-a) |
| `DEMO_USER_ID` | `a0000000-0000-4000-8000-000000000001` | **아래 경고 참고** |
| `DEMO_TODAY` | `2026-09-01` | 비우면 실제 KST 날짜를 쓴다 |
| `GEMINI_API_KEY` | B가 Google AI Studio에서 만든 값 | 서버 전용, `NEXT_PUBLIC_` 접두사 금지 |
| `GEMINI_MODEL` | `gemini-3-flash-preview` | Gemini 무료 tier 대상 모델. 필요 시 교체 |

PR Preview URL 대상으로 `test/api-smoke.mjs`를 돌릴 때는 같은 값을 Preview 환경에도 넣는다.
Production에만 넣으면 Preview 배포 자체는 성공해도 API route가 500을 반환한다.

> **`DEMO_USER_ID`를 반드시 넣을 것.** 미설정 시 API 라우트가 "가장 먼저 온보딩한
> 사용자"를 고르는데, 현재 DB에는 데모 계정 외에 2026-09-03에 생성된 계정이 하나 더
> 있다(계약 0건). 이 계정이 잡히면 화면이 빈 상태로 뜬다. 근거는 이슈 #23 검증 코멘트.

## 2. 배포 후 검증

### 2-1. API 스모크

```bash
API_BASE=https://<배포url> node test/api-smoke.mjs
```

0~5단계를 자동 검증한다. 실패 0건이어야 한다. 종료 코드로 성공을 판정할 수 있다
(성공 0 / 실패·중단 1).

**4단계가 데모 계약을 실제로 `risk`로 바꾸고 임시 유저를 남긴다.** 데모 직전이라면
`--skip-mutating`으로 돌리고, 이미 돌렸다면 재시드한다.

```bash
API_BASE=https://<배포url> node test/api-smoke.mjs --skip-mutating
```

### 2-2. 재시드

스모크가 데모 데이터를 오염시켰거나 상태가 의심스러우면 Supabase SQL Editor에
`db/seed-demo.sql`을 그대로 붙여넣는다. 먼저 지우고 넣으므로 몇 번을 실행해도 같은
상태가 된다.

`db/seed-demo.sql`은 `src/shared/mock-data.json`에서 생성한 산출물이다. 직접 고치지 말고
재생성한다.

```bash
node db/seed-demo.mjs > db/seed-demo.sql
```

## 3. 3분 데모 리허설

대본 원본은 `docs/mvp-spec-v3.md` 12장이다. 여기에는 **실측으로 확인된 숫자**만 적는다.

| 시각 | 동작 | 확인할 숫자 |
|---|---|---|
| 0:00 | 홈 진입 | 기준 29일 · 낙관 53일 · 비관 13일 |
| 0:20 | 캘린더 | 9월 6일부터 주의, 9월 26일부터 위험 |
| 0:45 | 카톡 계약문 붙여넣기 | AI 후보 추출 (#7) |
| 1:10 | 확인 후 등록 | 예정입금일·D-day 갱신 |
| 1:35 | 계약을 위험으로 지정 | 2026-09-30 → **2026-09-14** (16일 앞당겨짐) |
| 2:00 | (1:35 이후 이어서) 선금 100만원 9/14 · 카드 결제 2주 연기 가정을 나란히 비교 | 2026-09-14 → **2026-09-26**(+12일) / **2026-09-20**(+6일) |
| 2:25 | 입금 확인 | **P1 기능 — 아래 참고** |
| 2:45 | 마무리 | 계산은 규칙 기반, AI는 비정형 계약을 데이터화 |

> **[2026-09-06 정정, [#8](https://github.com/hsoo23/goreuge-mvp/issues/8)]** 2:00은 원래
> 선금 500,000원/9-15 가정이었으나, 1:35 "다음에 이어서" 실행하면(실제 리허설 순서)
> 입금일이 위험 전환 이후 D-day(09-14)보다 하루 늦어 효과가 0일이 되는 것을 확인했다.
> 위험 전환 이후에도 정상 동작하는 값(선금 100만원/9-14 + 카드 결제 2주 연기)으로
> 교체했고, 두 대응안을 카드 2장으로 나란히 보여준다. **재시드 없이 1:35 → 2:00을
> 끊지 않고 연속으로 진행할 수 있다.**

1:35와 2:00은 리허설 "회차" 사이에는 재시드한다. 1:35가 계약 상태를 영구히 바꾸므로
**2회차 리허설은 재시드 없이는 같은 숫자가 나오지 않는다** — 단, 같은 회차 안에서
1:35 → 2:00으로 이어가는 것은(위 정정 이후) 문제 없다.

> **2:25 구간은 P1 기능을 시연한다.** 기획서 10장이 `입금 확인과 실제 공제율 역산`을
> P1로 분류했고(`engine-interface.md` 3-9도 같다), P0 11개 목록에는 없다. 즉 P0를 전부
> 구현해도 이 구간은 시연할 수 없다. 대본에서 빼거나 P1을 앞당기거나 둘 중 하나를
> 정해야 리허설 대본이 확정된다. 상세는 이슈 #9 코멘트 참고.
>
> 6-3 표에 이 기능들이 있다고 P0인 것은 아니다. 6-3은 정산함 화면의 기능 명세이고,
> **우선순위의 출처는 10장이다.**

## 4. 제출 전 최종 점검

### 4-1. 키·개인정보 미포함

**반드시 `origin/main`을 기준으로 돌린다.** 로컬 `main`은 다른 워크트리에 체크아웃돼
있으면 뒤처져 있을 수 있고, 그러면 최신 커밋에 들어온 키를 놓친다.

```bash
git fetch origin
git grep -nIE "(eyJ[A-Za-z0-9_-]{30,})|(sk-[A-Za-z0-9]{20,})|(AIza[A-Za-z0-9_-]{20,})|(sb_secret_[A-Za-z0-9_-]{10,})|(service_role)|(-----BEGIN [A-Z ]*PRIVATE KEY)" origin/main -- . ':!*.lock' ':!package-lock.json' ':!docs/release.md' ':!scripts/deploy.sh'
git ls-tree -r --name-only origin/main | grep -E "\.env"
git log --all --diff-filter=A --name-only --format="" | sort -u | grep -E "\.env($|\.local|\.production)"
git grep -nIE "01[0-9]-[0-9]{3,4}-[0-9]{4}|[A-Za-z0-9._%+-]+@(gmail|naver|daum|kakao|hanmail)\.[a-z]{2,3}" origin/main -- . ':!*.lock' ':!package-lock.json'
```

1·3·4번은 결과가 없어야 한다. 2번은 `.env.example`과 `web/.env.example` 둘만 나와야 하고,
두 파일 모두 값이 비어 있어야 한다.

휴대폰·이메일 패턴에서 UUID가 오탐으로 걸리지 않게 앞자리를 `01`로 고정했다. 범용
`[0-9]{3}-[0-9]{3,4}-[0-9]{4}`를 쓰면 `d0000000-0000-4000-8000-…` 같은 시드 UUID가
전부 걸린다.

### 4-2. 합성 데이터·세무 제한 고지

- 시드 인물은 합성 페르소나(김도현)이며 실제 인물이 아니다. `docs/synthetic-data.md` 참고.
- 기획서 13장 고정 문구가 **사용자가 실제로 지나가는 경로에** 노출되는지 확인한다.

  > 고르게의 금액은 사용자가 입력하거나 확인한 정보를 바탕으로 한 현금흐름
  > 시뮬레이션입니다. 세금 신고, 소득유형 판정 또는 금융 의사결정을 대신하지 않습니다.

  `policy.ts`의 `FIXED_COPY.serviceDisclaimer`가 원본이다. 문구를 화면에 직접 쓰지 말고
  이 상수를 import 한다.

### 4-3. 기능명세와 구현 일치

**우선순위의 출처는 `docs/mvp-spec-v3.md` 10장이다.** 6장은 화면별 기능 명세이므로 거기
실려 있다고 P0인 것이 아니다. 10장 P0 11개가 실제로 동작하는지 화면에서 확인한다.

엔진 쪽은 `src/shared/engine-interface.md`가 선언한 함수와 `src/engine/` 구현을 대조한다.
현재 13개 중 11개가 구현돼 있고, 빠진 `confirmPayment`(3-9)와
`recalculateClientStats`(3-10)는 **둘 다 P1**이라 P0 범위에는 구멍이 없다.

`recalculateClientStats`가 없어 거래처 지연 통계는 시드값으로 고정이다. 계약을 등록해도
`completedCount`가 늘지 않아 신규 거래처는 계속 cold_start 정책값(0/7/21일)을 쓴다.
실측 D-day가 이 전제로 계산된 값이므로 **데모 숫자에는 영향이 없다.**

### 4-4. 제출본 태그

모든 P0가 머지되고 배포 URL이 확인된 뒤에 만든다.

```bash
git tag -a submission-v1 -m "금융 AI Challenge MVP 제출본"
git push origin submission-v1
```

## 5. 머지 순서 주의

브랜치가 서로 위에 쌓여 있어 순서에 따라 내용이 유실될 수 있다.

- **#25 → #29** — #29는 #25 위에 쌓였지만 마지막 커밋을 아직 담고 있지 않다. #29를 먼저
  머지하면 그 수정이 main에 들어가지 않는다.
- **#27은 #29에 포함된다** — #29가 #27의 커밋을 이미 담고 있다. #29를 머지하면 #27은
  불필요하다. 둘 다 열어두면 같은 충돌을 두 번 해소하게 된다.
- **`web/.env.example`** — #21이 머지되면서 #27·#29가 이 파일에서 충돌 상태가 됐다.
  내용 충돌이 아니라 위치만 겹치므로, 들어오는 `OPENAI_*` 블록을 살리면 된다.
