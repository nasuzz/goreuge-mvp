## 0. 서비스 정의

### 0-1. 서비스가 답하는 질문

> 아직 들어오지 않은 프로젝트 대금이 지연될 때, 나는 언제까지 버틸 수 있고 무엇을 바꿔야 하는가?

고르게는 프리랜서·N잡러의 계약대금, 입금 지연, 고정지출을 하나의 현금흐름으로 연결하여 **위험일(D-day)**과 대응 가능한 선택지를 보여주는 서비스다.

### 0-2. MVP의 단일 핵심 흐름

```text
카톡·메일 계약 내용 붙여넣기
→ AI가 계약정보 후보 추출
→ 사용자가 확인·수정
→ 예정입금일과 예상 실수령액 계산
→ 낙관·기준·비관 D-day 산출
→ 정산 상태가 바뀌면 D-day 즉시 갱신
→ 대응안을 가정하여 +N일 비교
```

이 흐름에 직접 기여하지 않는 기능은 P1 또는 P2로 둔다.

### 0-3. 구현 우선순위

| 등급 | 의미 |
|---|---|
| **P0** | 실제로 동작해야 하며, 없으면 핵심 주장이 성립하지 않음 |
| **P1** | 시간 내 가능하면 구현하는 보조 기능 |
| **P2** | 화면·기획 또는 향후 로드맵으로만 제시 |

## 1. 사용자와 핵심 상황

### 대표 페르소나

**김도현, 31세, 영상편집 프리랜서 5년 차**

- 동시 계약 4~6건, 거래처 6곳
- 현재 전체 계좌 잔액은 80만원
- 완료했지만 아직 받지 못한 계약대금은 912만원
- 카드 청구일과 월세일은 다가오지만 거래처 입금일은 자주 늦어짐
- 문제는 돈을 못 번 것이 아니라 **번 돈이 아직 들어오지 않은 것**

### 핵심 사용자 가치

1. 받을 돈이 어디에 얼마나 묶여 있는지 본다.
2. 입금이 늦을 때 잔액이 언제 위험해지는지 본다.
3. 선금 요청, 지출 연기 등 선택이 D-day를 며칠 바꾸는지 비교한다.
4. 실제 공제 내역을 기록하고 사용할 수 없는 준비금을 분리한다.

## 2. 정보 구조 — 4개 화면

| 메뉴 | 역할 | 우선순위 |
|---|---|---|
| **홈(위클리)** | D-day, 가용금액, 위험 원인, 이번 주 입금, 대응안 | P0 |
| **캘린더(먼슬리)** | 입금·유출·위험일과 일별 예상잔액 | P0 |
| **정산함** | 계약 등록, 대기·지연·위험, 입금 확인 | P0 |
| **위시함** | 구매 영향, 주간 적립, 살 수 있는 날 | P1 |

### 구조 원칙

- 앱 첫 화면은 **홈(위클리)**이다.
- 정산함은 서비스 핵심이므로 데일리 하위에 숨기지 않고 독립 메뉴로 둔다.
- 지출 입력은 독립 페이지가 아니라 전역 `+` 버튼 또는 홈의 빠른 입력으로 제공한다.
- 다이어리 무드는 위클리·먼슬리 명칭, 캘린더, 체크 방식에 남긴다.
- D-day는 홈에서 가장 크게 보여주고, 캘린더에는 작은 공통 지표로 표시한다.

## 3. 온보딩 정책

온보딩은 최초 결과를 만드는 데 필요한 값만 받는다. 계약은 온보딩 이후 정산함에서 등록한다.

### 3-1. 필수 입력

| 항목 | 입력 방식 | 저장값 | 기본 정책 |
|---|---|---|---|
| 현재 잔액 | 금액 1개 | `user.total_balance` | 전체 입출금 가능 계좌 합계 |
| 월 필수지출 | 금액 1개 | `user.monthly_fixed_outflow` | 다음 30일에 일할 반영 |
| 안전예비금 | 제안값 확인·수정 | `user.safety_buffer` | 월 필수지출 1개월치 |

### 3-2. 현재 잔액의 고정 정의

사용자에게 선택지를 주지 않고 다음 정의로 통일한다.

> 생활비 계좌, 세금 준비 계좌, 위시 적립 계좌 등 현재 보유한 입출금 가능 계좌의 잔액을 모두 합산해 입력해 주세요.

투자계좌, 해지 전 사용할 수 없는 예·적금, 신용카드 한도는 포함하지 않는다.

### 3-3. 안전예비금

```text
기본 안전예비금 = 월 필수지출 × 1.0개월
```

화면 문구:

> 월 필수지출을 기준으로 1개월치인 1,200,000원을 안전예비금으로 제안해요. 예상 지출이 아니라, 가용자금 계산에서 건드리지 않는 기준선이에요.

사용자는 제안값 사용, 직접 수정, 0원으로 시작 중 하나를 선택할 수 있다. MVP 상수는 `SAFETY_BUFFER_MONTHS = 1.0`으로 둔다.

### 3-4. 월 필수지출 베이스라인

온보딩에서는 항목별 월세·통신비를 받지 않고 총액 한 번만 받는다.

```text
매달 고정적으로 나가는 돈이 얼마나 되나요?
월세, 통신비, 보험료, 구독료, 대출 상환 등을 대략 합산해 주세요.

[ 1,200,000 ]원
나중에 정확한 항목과 날짜를 추가할 수 있어요.
```

MVP의 일별 시뮬레이션에서는 다음처럼 일할 반영한다.

```text
일별 필수지출 베이스라인 = monthly_fixed_outflow ÷ 30
```

월 총액을 매월 1일에 전액 차감하면 실제와 무관한 위험 절벽이 생기므로 사용하지 않는다. 카드 청구액·월세처럼 금액과 날짜를 별도 등록한 `outflow`는 해당 날짜에 반영하며, 향후 항목별 등록이 완성되면 같은 금액을 베이스라인에서 제외해 중복 차감을 방지한다.

### 3-5. 세금 준비율

세금 준비율은 법정 세율이나 예상 세액이 아니라 사용자의 현금 보호 정책이다.

| 프리셋 | 준비율 | 설명 |
|---|---:|---|
| 가볍게 시작 | 10% | 적은 금액부터 분리 |
| **기본** | **12%** | MVP 기본 선택값 |
| 여유 있게 | 15% | 더 많은 금액을 보호 |
| 직접 설정 | 사용자 입력 | 0~50% 범위 |

고정 안내 문구:

> 사용자가 현금흐름 관리를 위해 설정하는 준비 비율이며, 세율 또는 예상 세액이 아닙니다.

소득유형별 준비율 자동 추천은 P2로 미룬다.

### 3-6. 건너뛸 수 있는 항목

- 데모 계정 선택
- 세금 준비율 설정
- 개별 고정지출 등록
- 위시 등록

## 4. D-day 및 현금흐름 엔진

### 4-1. 잔액 구성요소

```text
현재 실질 가용잔액
= 전체 계좌 합계
- 실제 보호 완료한 세금 준비금
- 실제 적립 완료한 위시 준비금
- 안전예비금
```

보호·적립 체크가 완료된 금액만 현재 가용잔액에서 제외한다. 앞으로 적립할 금액은 해당 예정일의 미래 유출로 한 번만 반영한다.

### 4-2. 일별 시뮬레이션

```text
예상잔액[d]
= 예상잔액[d-1]
+ d일 시나리오별 예상 실수령액
- d일 확정 유출
- d일 필수지출 베이스라인
- d일 신규 적립 예정액

D-day
= 예상잔액[d] <= 안전예비금이 되는 최초 날짜
```

현재 실질 가용잔액을 시작값으로 사용한다면 안전예비금을 시작 시점에서 이미 차감하고 D-day 기준은 `0 이하`로 계산해도 된다. 구현에서는 둘 중 하나만 사용하며 중복 차감하지 않는다. 본 MVP는 다음 방식으로 고정한다.

```text
simulation_start_balance
= total_balance
- reserved_tax_amount
- reserved_wish_amount
- safety_buffer

D-day = projected_balance[d] <= 0인 최초 날짜
```

### 4-3. 예상 입금액

우선순위는 다음 하나로 통합 관리한다(이슈 #16 확정).

| 순위 | 조건 | 예상 실수령액 | status |
|---|---|---|---|
| 1 | 실제 입금 확인 완료 | 실제 실수령액(잠정값 폐기) | `actual` |
| 2 | 지급처가 실수령액을 금액으로 안내함 | 안내받은 금액 그대로 | `calculated` |
| 3 | 사용자가 소득유형·참조율 적용을 확인함 | `계약 총액 - Math.floor(총액 × 사용자 확인 예상율)` | `calculated` |
| 4 | 그 외 | 없음 → `추정 불가` 배지 | `unavailable` |

- 2순위는 `payerStatedNetAmount: Won | null`에 **원 단위 금액 그대로** 저장한다.
  공제율로 환산해 `confirmedExpectedRate`에 넣지 않는다 — DB 컬럼이 `numeric(5,4)`라
  왕복 시 원 단위가 어긋난다(실측 최대 241원 차).
- 지급처가 "공제액 79,200원"처럼 **공제액**으로 알려준 경우에는 계약 총액에서 차감해
  **실수령액**으로 바꾼 뒤 저장한다. 이 필드는 공제액이 아니라 실수령액이다.
- 2순위와 3순위는 화면 문구가 다르다(5-3). 값의 출처를 별도 enum으로 두지 않고
  `payerStatedNetAmount`가 null인지로 판별한다 — 중복 상태를 만들지 않기 위해서다.

### 4-4. 입금 지연 시나리오

정시율을 금액에 곱하지 않는다. 실제로 존재하지 않는 부분 입금을 만들지 않기 위해 **금액은 유지하고 입금일을 이동**한다.

#### 신규 거래처 — 전역 정책값

| 시나리오 | 입금일 |
|---|---|
| 낙관 | 예정입금일 |
| 기준 | 예정입금일 + 7일 |
| 비관 | 예정입금일 + 21일 |

```yaml
cold_start_delay:
  optimistic_days: 0
  baseline_days: 7
  pessimistic_days: 21
  policy_version: "mvp-1"
```

#### 입금 완료 이력 3건 이상 거래처

| 시나리오 | 입금일 |
|---|---|
| 낙관 | 예정입금일 |
| 기준 | 예정입금일 + 지연일 중앙값 |
| 비관 | 예정입금일 + 지연일 p90 |

화면에는 데이터 근거를 표시한다.

> 거래 이력이 부족해 신규 거래처 기본 지연값을 사용했어요.

### 4-5. 상태 처리

| 상태 | 조건 | 시뮬레이션 처리 |
|---|---|---|
| 대기 | 예정일 전, 미입금 | 시나리오별 입금일 적용 |
| 지연 | 예정일 경과, 미입금 | 오늘 이후 지연 정책 적용 |
| 위험 | 60일 이상 미입금 또는 수동 지정 | 기준·비관에서는 기간 내 유입 제외 |
| 완료 | 실제 입금 확인 | 실제일·실수령액 반영 |
| 취소 | 계약 취소 | 유입 0원 |

### 4-6. 주간 가용금액

```text
28일 안전자금
= simulation_start_balance
+ 28일 내 기준 시나리오 유입
- 28일 내 확정 유출
- 28일 필수지출 베이스라인
- 28일 내 신규 적립 예정액

이번 주 가용금액 = max(0, 28일 안전자금) ÷ 4
```

결과 화면에는 잔액·유입·유출·보호분을 분해해 합계가 일치하도록 보여준다.

## 5. 시스템 참조 공제율

### 5-1. 원칙

- 온보딩 입력값이 아니라 시스템 설정 데이터다.
- 소득유형을 AI가 확정하지 않는다.
- AI는 계약 문장에서 소득유형 **후보**만 제안한다.
- 사용자가 후보를 확인한 후에만 참조율을 잠정 실수령액에 적용한다.
- 참조율은 실제 세액이나 최종 공제율을 보장하지 않는다.

### 5-2. 참조 데이터

| income_type | 화면명 | 참조율 | 처리 |
|---|---|---:|---|
| `business_personal_service` | 원천징수 대상 인적용역 사업소득 | 3.3% | 사용자 확인 후 잠정 적용 |
| `qualifying_other_income` | 일부 기타소득 | 8.8% | 적용 조건 확인 후 잠정 적용 |
| `employment_income` | 근로소득 | 없음 | 간이세액표 등에 따라 달라 추정 불가 |
| `no_withholding` | 공제 없는 수입 | 0% | 사용자 확인 후 적용 |
| `needs_review` | 확인 필요 | 없음 | 총액 표시, 실수령액 추정 불가 |

기타소득 8.8%는 모든 기타소득에 일괄 적용하지 않는다. 설정 파일에는 조건·출처·확인일을 함께 둔다.

```yaml
withholding_references:
  - income_type: business_personal_service
    reference_rate: 0.033
    includes_local_income_tax: true
    requires_user_confirmation: true
    source: "국세청"
    checked_at: "2026-08"

  - income_type: qualifying_other_income
    reference_rate: 0.088
    includes_local_income_tax: true
    requires_user_confirmation: true
    note: "모든 기타소득에 동일하게 적용되지 않음"
    source: "국세청"
    checked_at: "2026-08"
```

### 5-3. 계약 등록 화면 로직

```text
1. AI가 계약정보·소득유형 후보와, 지급처가 실수령액을 알려준 문장이 있으면 그 금액도
   후보로 제시한다. AI는 후보만 내고 값의 출처를 확정하지 않는다.
2. 사용자가 소득유형을 확인하고, 지급처 안내 금액 후보가 있으면 그 금액을 확인한다.
3. 지급처 안내 금액을 확인했으면 그 금액을 그대로 쓰고, 없으면 확인된 참조율로 잠정
   실수령액을 계산한다.
4. 둘 다 미확인이면 추정 불가 배지를 표시한다.
5. 실제 입금 확인 후 실제값으로 교체한다.
```

예시 — 참조율을 승인한 경우(안내 문구 있음):

```text
D에이전시 편집 · 총액 2,400,000원
소득유형 후보: 인적용역 사업소득       [확인]
예상 실수령액: 2,320,800원
※ 확인 전 추정치이며 3.3% 참조율을 적용했습니다.
```

예시 — 지급처가 금액을 직접 안내한 경우(**안내 문구를 붙이지 않는다**):

```text
D에이전시 편집 · 총액 2,400,000원
소득유형: 인적용역 사업소득
예상 실수령액: 2,320,800원 (지급처 안내)
```

추정치도 아니고 참조율을 적용한 것도 아니므로 `※ 확인 전 추정치…` 문구를 붙이면
사실과 다르다. 화면은 `payerStatedNetAmount !== null`로 두 경우를 분기한다.

실제 입금 확인 시:

```text
실제 공제율 = (계약 총액 - 실제 실수령액) ÷ 계약 총액
```

참조율(`referenceRate`), 사용자 확인 예상율(`confirmedExpectedRate`),
실제율(`actualRate`)은 서로 다른 필드로 저장한다. 지급처가 안내한 실수령액은
율이 아니라 금액이므로 네 번째 필드 `payerStatedNetAmount`에 따로 저장한다(4-3).

## 8. AI 명세

### 8-1. 핵심 AI — 계약 텍스트 구조화

입력 예시:

> 편집본은 9월 3일 납품이고 총 240만원이에요. 검수 끝나면 익월 말일에 지급할게요.

출력 후보:

```json
{
  "client_name": null,
  "gross_amount": 2400000,
  "completion_date": "2026-09-03",
  "settlement_term": "NEXT_MONTH_END",
  "income_type_candidate": "needs_review",
  "confidence": {
    "gross_amount": 0.98,
    "completion_date": 0.96,
    "settlement_term": 0.91,
    "income_type_candidate": 0.31
  }
}
```

규칙:

- 필드별 confidence를 반환한다.
- 낮은 confidence 필드는 강조한다.
- 거래처 실명·계좌번호는 마스킹 후 전송한다.
- AI가 소득유형을 최종 판정하지 않는다.
- 사용자 확인 전 DB에 계약을 저장하지 않는다.
- 예정입금일과 금액은 결정론 엔진에서 계산한다.

### 8-2. 보조 AI

| 기능 | 역할 | 제한 |
|---|---|---|
| 독촉 문구 | 계약정보로 메시지 초안 생성 | 자동 발송 금지 |
| 위험 설명 | 엔진 결과를 2~3문장으로 서술 | 금액 직접 계산 금지 |

### 8-3. AI 평가

직접 만든 계약 문장 20건으로 평가한다.

| 평가 항목 | 목표 |
|---|---:|
| 금액 추출 정확도 | 95% 이상 |
| 완료일 추출 정확도 | 90% 이상 |
| 정산조건 추출 정확도 | 85% 이상 |
| 사용자 확인 없이 저장된 건 | 0건 |

LLM 실패 시 수기 입력 화면으로 전환하며 D-day 서비스는 계속 동작한다.

| 하는 것 | 하지 않는 것 |
|---|---|
